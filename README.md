# Soup Kernel Challenge — Решение команды Sert Team

Оптимизация дообучения **Qwen2.5-1.5B-Instruct** (4-bit NF4 + LoRA r=16) на GPU NVIDIA Tesla T4
в рамках соревнования Soup Kernel Challenge (Decentrathon 6.0). Всё решение — собственные
Triton-ядра и системные патчи в `solution/`, поверх неизменённого официального пайплайна Soup 0.77.0.

**Публичный Kaggle Notebook с сохранённым выводом (Run All на финальном коммите):**
https://www.kaggle.com/code/azeibarjanec/sert-team-submission

## Итог в двух числах

| | Базовый Soup 0.77.0 | Наше решение | Выигрыш |
|---|---|---|---|
| Полное время `soup train` | 80.35 с | **54.22 с** | **ускорение 1.4819x** |
| Пиковая VRAM | 14,345 MiB | **5,403 MiB** | **экономия 2.655x** |

Качество обучения не деградировало: eval loss −0.152% относительно базового (в пределах допуска 0.5%),
все 10 официальных проверок `check_rules.py` — **10/10 PASS**; доля собственного Triton-кода —
**14.5% времени шага** (порог ≥ 5%).

## 1. Архитектура решения

Профиль базового Soup на T4 показал четыре главных потребителя ресурсов:

1. **Элементные операции и касты типов (~44% времени GPU)** — разрозненные вызовы PyTorch для
   RMSNorm, RoPE и SwiGLU с постоянными приведениями FP32 ↔ FP16.
2. **Cross-Entropy над словарём в 151,936 токенов** — полный тензор логитов `[B·T, V]`
   материализуется трижды за шаг (~5 ГБ VRAM).
3. **Холостая работа на паддинге** — ~25% строк батча являются pad-токенами.
4. **Хранение активаций** — большой FP32 residual stream и кэш активаций LoRA.

### Собственные Triton-ядра (9 ядер, запускаются на каждом шаге)

- **`rmsnorm_fwd_kernel` / `rmsnorm_bwd_dx_kernel` (`solution/rmsnorm.py`)** — RMSNorm одним
  запуском ядра на строку: дисперсия в FP32, `rsqrt`, нормализация и взвешивание в одном проходе;
  построчный `rstd` кэшируется для обратного прохода (подход Liger-Kernel, реализация с нуля
  под архитектуру sm75, `num_warps=8`).
- **`rope_fwd_kernel` / `rope_bwd_kernel` (`solution/rope.py`)** — поворотное позиционное
  кодирование с прямой поддержкой 4D-страйдов транспонированных тензоров `[B, H, T, D]` и
  `cos/sin` формы `[1, T, D]`; убирает ~4,500 мелких запусков PyTorch-ядер за прогон.
- **`ce_tile_stats_kernel` / `ce_bwd_dlogits_kernel` (`solution/chunked_ce.py`)** — потоковая
  (chunked) Cross-Entropy: полный тензор логитов никогда не материализуется. В обратном проходе
  GEMM и градиент по логитам считаются только для активных токенов (`targets >= 0`),
  пропуская строки паддинга и промпта.
- **`swiglu_fwd_kernel` / `swiglu_bwd_kernel` (`solution/swiglu.py`)** — слияние активации
  `SiLU(gate) * up` и её обратного прохода в одно ядро каждый.
- **`nf4_dequant_kernel` (`solution/nf4_dequant.py`)** — собственная распаковка NF4-весов:
  ниббли → кодовая книга (16 fp32-значений) → умножение на построчный absmax с поддержкой
  double-quant (деквантование самих масштабов blockwise). Заменяет внутреннюю деквантацию
  bitsandbytes, время которой не учитывалось как собственный Triton-код.

### Системные оптимизации

- **Per-use NF4 деквантование вместо кэша весов (`solution/nf4_dequant.py`).** Замороженные
  4-bit проекции распаковываются собственным ядром непосредственно перед каждым использованием
  (forward и backward). Автоградиентная обёртка (zero-save autograd Function) не сохраняет
  активаций для замороженных весов — градиент по входу считается через повторную распаковку.
  Это убирает ~2.6 ГБ FP16-кэша весов и делает распаковку замороженных весов частью
  собственного Triton-кода. Корректность побитово сверена с bitsandbytes на CPU-бэкенде
  (5 сценариев, включая fp16-состояния, нечётные размеры и вложенное double-quant).
  Макет NF4 соответствует QLoRA (Dettmers et al., 2023).
- **Post-import precompile (`solution/precompile.py`).** Фоновый поток прогревает все
  собственные ядра на маленьких dummy-тензорах той же специализации, что и реальные
  (constexpr, кратность 16), пока строится модель. Компиляция Triton уходит с критического
  пути замера: −4–5 с wall-времени, нулевой риск для чисел.
- **FP16 residual stream + FP16 tied embedding (`solution/residual_fp16.py`, `solution/embed_fp16.py`).**
  Поток остаточных связей переведён в FP16 (меньше трафика GDDR6 и объёма сохраняемых
  активаций); замороженная tied-таблица `embed_tokens` хранится в FP16 без потери точности
  (−445 MiB).
- **Обучение только на реальных токенах (`solution/unpad.py`, Fix 1A)** — изолированная
  обработка pad-строк, устраняющая баг экспоненциального удвоения паддинга (см. §4).

## 2. Как воспроизвести

### Ссылки
- **Репозиторий команды (платформа):** https://github.com/avantyur1st/soup-final-solution
- **Публичный Kaggle Notebook с сохранённым выводом:**
  https://www.kaggle.com/code/azeibarjanec/sert-team-submission

### Запуск на Kaggle T4
1. Открыть указанный Kaggle Notebook.
2. В панели справа выбрать ускоритель **GPU T4 x2** и включить **Internet: On**.
3. Нажать **Run All**. Ноутбук — неизменённый официальный шаблон соревнования, в котором
   указаны только `REPO_URL` (этот репозиторий) и `COMMIT` (SHA финального коммита).
4. Скрипт склонирует репозиторий на зафиксированном SHA и запустит официальный замер
   `harness/run_task.py`.
5. В `runs/result.json` и `runs/checks.json` будут зафиксированы метрики и все 10 проверок
   (**10/10 PASS**).

Локально: склонировать репозиторий, на машине с CUDA-совместимой GPU выполнить
`python harness/run_task.py --solution solution/` — замер прогонит базовый Soup и решение
в одной сессии и запишет `runs/result.json`, `runs/checks.json`.

## 4. Честный анализ: ограничения и уроки

### Преодолённые сложности
- **Удвоение паддинга:** в ранних версиях `unpad.py` `flat.index_copy` удваивал значения
  pad-строк на каждом из 28 слоёв, что на FP16 residual stream приводило к overflow и NaN-градиентам.
  Решено разделением путей обработки pad и valid токенов (Fix 1A).
- **Порог по доле собственных ядер (Check 4, ≥ 5%):** чем сильнее ускоряется шаг, тем ниже доля
  вспомогательных ядер. Долю удалось поднять структурно — 4.5% → 7.7% → **14.5%** — собственной
  распаковкой NF4: время, которое раньше проводила внутренняя (не засчитываемая) деквантация
  bitsandbytes, теперь исполняется нашим `@triton.jit`-ядром.
- **FP16-численная стабильность:** наивные попытки хранить входы RMSNorm в FP16 без масштабирования
  теряли градиенты; переход на rstd-кэш обеспечил точное следование кривой лосса базовой линии.

### Текущие ограничения
- Per-use деквантование NF4 тратит время на каждом шаге (входит в 14.5% собственного кода):
  вариант с кэшированием деквантованных весов быстрее по wall, но использует ~2.6 ГБ VRAM
  и даёт более низкий итоговый балл по официальной формуле.
- Выигрыш `unpad.py` снижается, если в данных нет паддинга.
- Ускорение — отношение к базе той же сессии: абсолютное wall-время может отличаться между
  прогонами, соотношение стабильно (жюри сравнивает с собственной базовой линией).

## 5. Источники идей

Механизмы опираются на опубликованные методы: QLoRA / NF4 (Dettmers et al., 2023),
Liger-Kernel (fused RMSNorm / SwiGLU), online softmax (Milakov & Gimelshein, 2018),
FlashAttention-стиль тайлинга для потоковой Cross-Entropy. Весь код в `solution/` написан
с нуля; сторонний GPU-код только читался и не копировался.
